How Stable Are LLM-Generated Proofs Under Program Refactoring? A Stress Test for Verifiable Code Generation

Aravind Mandiga, Guoming Li

cs.AI Oct 26, 2026 · v1 cs.LO cs.SE
benchmark verification theorem-proving-ml
Read PDF arXiv abstract Code
TL;DR
Builds a benchmark of Lean-certified behavior-preserving refactorings of VERINA tasks and re-checks fixed Lean proofs against them to measure proof survival.
Abstract
Benchmarks for verifiable code generation usually test a proof against one fixed implementation. We ask whether the same proof remains valid after a program refactoring that preserves behavior. We introduce RefactorProof, which derives 458 Lean-certified variants from the 185 VERINA tasks that compile in our pinned environment while holding the specification and evaluated proof fixed byte-for-byte. VERINA supplies reference proofs for 46 tasks, all from its basic split; the primary model-versus-reference comparisons further match on 21-25 short, non-recursive tasks. Structural refactorings expose substantial brittleness across proof sources: task-normalized structural PSR is 4.3% for the supplied references and 13.3-26.8% for the specialized provers. On the matched tasks, specialized prover proofs nevertheless have higher overall unchanged-proof survival than the supplied reference artifacts: +15.6 points for DeepSeek-Prover-V2-7B, +18.8 for Goedel-Prover-V2-32B, and +20.3 for Goedel-Prover-V2-8B; all three 95% CIs exclude zero. The ordering persists after excluding universally survived T1 variants, under family-balanced aggregation, and under alternative deployable valid-proof selection rules. However, unchanged-proof failure is not the same as high repair cost: predefined one-identifier edits repair 51/54 eligible reference structural failures and 58/85 eligible prover failures. RefactorProof therefore measures unchanged-proof stability under program refactoring, not the cost of maintaining a proof after it breaks.
Problem

Benchmarks for verifiable code generation check a proof against one fixed implementation. It is unclear whether LLM-generated and reference proofs stay valid after behavior-preserving refactorings of the program.

Approach

RefactorProof applies five deterministic transformation families (let-introduction, helper extraction, commutative swap, condition inversion, branch extraction) to the implementations of VERINA tasks. Each variant is kept only if Lean proves its equivalence to the original in a separate file. The specification and proof are held byte-identical, and the unchanged proof is then re-checked against the new implementation. Proof survival rate (PSR) is compared across reference proofs and specialized provers, with sensitivity analyses and a mechanical one-identifier repair experiment.

Results

The benchmark contains 458 certified variants from 185 tasks. Structural refactorings break most proofs: structural PSR is 4.3% for reference proofs and 13.3–26.8% for provers. On matched tasks, DeepSeek-Prover-V2-7B and Goedel-Prover-V2 proofs survive 15.6–20.3 points more often than the references. One-identifier edits repair 51/54 eligible reference structural failures and 58/85 eligible prover failures.
